How I fixed the authorisation hole in my Pokémon API

My Year 1 API checked if you were logged in, but not who you were.

In Year 1, I made a Pokémon battle game for my Back-End Development module. It was a REST API in Express with MySQL, with JWT login and bcrypt for passwords. It worked fine for the assignment. In October 2026 I wanted to put it online so anyone could play it, so I went back through the code first.

The problem

Most of the player routes looked like this:

router.post('/:user_id/purchase', jwtMiddleware.verifyToken, shopController.purchaseItem);

verifyToken checked that the token was real. But the controller used the user_id from the URL, and nothing checked that it matched the person logged in. So if I was logged in as user 2, I could call /api/shop/7/purchase and spend user 7’s coins. The team routes had the same problem.

There were other problems too. When a battle ended, the server took the result from the request, so you could just send "result": "win" and get the gym reward as many times as you wanted. Any logged-in player could also create or delete gyms.

I never noticed any of this when testing, because my own pages always sent the right id. It only shows up when someone sends requests to the API directly instead of using the site.

How I fixed it

I added a middleware called verifyOwner that runs after verifyToken. It checks that the user_id in the request is the same as the one in the token, and returns 403 if not:

module.exports.verifyOwner = (req, res, next) => {
  const requestedId = req.params.user_id ?? req.body.user_id;
  if (parseInt(requestedId) !== res.locals.userId) {
    return res.status(403).json({ message: "Forbidden: Not your account" });
  }
  next();
};

I put it on the shop, team, Pokédex and owned-Pokémon routes. Battles are now looked up by the battle id and the user id together, so you can’t touch someone else’s battle. Routes that change gyms, badges or Pokémon need an admin id from ADMIN_USER_IDS. The server now decides who won, and you only get a reward for a battle you actually won and haven’t claimed yet.

Making sure it stays fixed

Later I added 20 API tests, and some of them are only there to check these rules: you can’t buy, pick a starter or view a profile on someone else’s account, only admins can change gyms, and rewards are never paid without a win, never twice and never for someone else’s win. They run in GitHub Actions on every push and pull request, against a real PostgreSQL database.

What I learned

Before this I didn’t really get the difference between authentication and authorisation. Authentication is checking who you are. Authorisation is checking if you’re allowed to do something. My Year 1 code only did the first one. Now whenever a route takes an id, I check where it comes from and whether the user owns it, and I write a test that tries a wrong id.

There’s still one thing I want to clean up: the profile update and delete routes check ownership inside the controller instead of using the middleware. They’re still protected, but I’d rather have all the checks in one place.
