How I fixed the authorisation hole in my Pokémon API

My Year 1 API checked that you were logged in. It never checked who you were.

In Year 1 I built a Pokémon battle game for my Back-End Development module: an Express REST API over MySQL, with JWT login and bcrypt password hashing. It did what the assignment asked. I came back to it in October 2026, when I decided to put it online for anyone to play.

Putting something on the public internet changes the question you ask of the code. In a demo, the only user is you. On a shared server, any request might come from someone poking at it to see what breaks. So before deploying, I went back through the routes.

The hole

Most player routes looked like this:

router.post('/:user_id/purchase', jwtMiddleware.verifyToken, shopController.purchaseItem);

verifyToken did its job. It rejected missing or forged tokens and stored the caller’s id in res.locals.userId. But the controller then used req.params.user_id, the number in the URL, and nothing compared the two. A player logged in as user 2 could call /api/shop/7/purchase and spend user 7’s coins. The team routes had the same pattern, so you could rearrange someone else’s team too.

There was a second problem in the same spirit. The end-battle endpoint read result from the request body, so a client could simply say it had won and collect the gym reward as often as it liked. And any logged-in player could create or delete gyms.

None of this showed up when I tested through the app’s own pages, because they always sent the right id. These bugs only appear once you stop trusting the client.

The fix

I added a small middleware that runs after verifyToken. It compares the account in the URL or body with the account in the token and answers 403 if they differ:

module.exports.verifyOwner = (req, res, next) => {
  const requestedId = req.params.user_id ?? req.body.user_id;
  if (parseInt(requestedId) !== res.locals.userId) {
    return res.status(403).json({ message: "Forbidden: Not your account" });
  }
  next();
};

It now guards the shop, team, Pokédex and owned-Pokémon routes. Battles are loaded by both their id and the caller’s id, so a battle that isn’t yours simply isn’t found. Routes that change shared game data need an admin id from ADMIN_USER_IDS, and nobody is an admin unless that is set. The server now decides who won, and a reward needs a won, unclaimed battle that belongs to you.

Keeping it fixed

A fix without a test can quietly come back. When I added an API test suite, several of its 20 tests exist only to attack these rules: one trainer’s token can’t buy, pick a starter or read a profile on another trainer’s account, only admins can change gyms, and a reward is never paid without a won battle, never twice and never for someone else’s win. They run in GitHub Actions against a real PostgreSQL database on every push and pull request.

What I took from it

Authentication answers “who are you?”. Authorisation answers “are you allowed to do this?”. My Year 1 code only asked the first question. Now, whenever I write a route that takes an id, I ask where that id comes from and whether the caller owns it, and I write the test that tries the wrong one.

One loose end is left: the profile update and delete routes still check ownership inside the controller instead of using the middleware. They’re protected, but I’d like every rule in one place.
