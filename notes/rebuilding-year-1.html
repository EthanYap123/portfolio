Rebuilding my Year 1 projects properly

Three of my Year 1 projects passed their assignments. None of them were ready for real users. Here’s what was wrong and what I changed.

In October 2026 I wanted every web project on my portfolio to have a live demo. That meant opening up code I’d written a year earlier and looking at it the way a stranger would. It was humbling. The problems weren’t exotic: they were the shortcuts you take when the only person using the app is you, the night before a deadline.

Pokémon battle API: trusting the client

The API checked that a request had a valid login token but never checked whose it was, so any player could spend another player’s coins by changing the id in the URL. The client also told the server who won each battle, so gym rewards could be claimed for free and more than once. A purchase ran as several separate queries, so a failure halfway through could take the coins without giving the Pokémon.

The fixes: an ownership check on every player route, battle results decided on the server, rewards only for a won and unclaimed battle, and each purchase run as one database transaction that locks the player’s row. I also moved it from MySQL to PostgreSQL, deployed it on Vercel with Neon, and added 20 API tests that run in CI. I wrote that part up in a separate note.

Retail dashboard: hard-coding everything

The front end called a fixed address, http://localhost:8081, so it only worked on my laptop. The payment methods were a hard-coded list, so the page broke as soon as the data held one I hadn’t typed in. On the server, the CSV path only worked from one folder, some number columns were read as text, and a failed load left the server half-started instead of stopping with a clear error.

Now the payment methods come from the data, every value is escaped before it goes into the page, and the CSV path works from anywhere. The biggest change was dropping the need for a server at all: a build step packs all 100,000 transactions into a compact JSON file, and a GitHub Actions workflow builds it and deploys the dashboard to GitHub Pages.

Mental Wellness Hub: the small things

Every page threw console errors, because one shared script assumed every page had every element. The tips carousel had two active slides, the favicon was missing, the navigation overflowed on phones, and the gratitude journal put whatever you typed straight into the page without escaping it.

I split the script per page so each one checks before it runs, escaped user input, and then did the accessibility work I’d skipped entirely in Year 1: labelled controls, live regions, visible focus styles and reduced-motion support. I checked every page at 375 px, 768 px and desktop widths, in light and dark mode.

What the three had in common

  • Trusting input. An id in a URL, a battle result from the client, text in a journal: all of it needs checking or escaping before it’s used.
  • Hard-coding what the data can tell you. Addresses, payment lists and file paths were all fine on my machine and wrong everywhere else.
  • Never running it anywhere else. Each problem was easy to miss until the app had to work on someone else’s screen.

The habit I’ve kept is to deploy early and test like a stranger. If I were starting these projects again, I’d also write the tests first. In the Pokémon rebuild the tests came a week after the fixes, and they’re the only thing that stops the same holes from coming back.
