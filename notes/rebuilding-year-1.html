Rebuilding my Year 1 projects properly

Three of my Year 1 projects passed, but they weren’t ready for real people to use. Here’s what was wrong and how I fixed them.

In October 2026 I wanted every web project on my portfolio to have a live demo. That meant going back to code I wrote a year ago and actually looking at it properly. Most of the problems weren’t complicated. They were shortcuts I took because I was the only one using the app.

Pokémon battle API

Any logged-in player could spend another player’s coins just by changing the id in the URL. The client also told the server who won a battle, so you could claim gym rewards without fighting, more than once. Buying something ran as a few separate queries, so if one failed halfway you could lose your coins and not get the Pokémon.

I added an ownership check on every player route, made the server decide who wins, and made each purchase run as one database transaction. I also moved it from MySQL to PostgreSQL, put it on Vercel with Neon, and added 20 API tests that run in CI. I wrote more about the first fix in another note.

Retail dashboard

The front end called http://localhost:8081, so it only worked on my laptop. The payment methods were a hard-coded list, so the page broke if the data had one I didn’t type in. On the server, the CSV path only worked from one folder, some numbers were read as text, and if loading failed the server kept running half-broken.

Now the payment methods come from the data, all values are escaped before they go into the page, and the CSV path works from anywhere. The biggest change was removing the server completely: a build step packs all 100,000 transactions into one JSON file, and GitHub Actions builds it and deploys the dashboard to GitHub Pages.

Mental Wellness Hub

Every page had console errors because one shared script expected every page to have the same elements. The carousel had two active slides, the favicon was missing, the nav overflowed on phones, and the journal showed whatever you typed straight on the page without escaping it.

I gave each page its own script, escaped all user input, and added the accessibility features I skipped in Year 1: labels on controls, live regions, focus styles and reduced motion. Then I checked every page at phone, tablet and desktop sizes, in light and dark mode.

What they had in common

  • I trusted input I shouldn’t have. An id in the URL, a battle result from the client, text in a journal.
  • I hard-coded things that should have been flexible, like the server address, the payment list and file paths.
  • I never ran them anywhere except my own computer.

What I do now is deploy early and test it like someone else would. If I did these again, I’d also write tests from the start. For Pokémon I only added tests a week after the fixes, and they’re what stops the same bugs from coming back.
